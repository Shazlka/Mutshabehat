# Review editor in the Qiraat iOS app: design

Date: 2026-10-05. Status: approved by the owner in chat (scope: full parity with the web editor in one
release, delivered in verified milestones; the written-spec review gate was waived by the owner).
Branch: `ios/review-editor` from `ios/main`.

## 1. Goal

A **developer-only** review editor inside the Qiraat iOS app that does what `/mushaf-1441/review` does on
the web: review every Qiraat variant from the phone, word by word, and approve it. The reviewer opens a
Mushaf page, taps a word, sees the recorded variants and the nquran and الشامل references, chooses the
category, saves and approves. Every save updates the live database through the web app's own review API,
with the same behaviour as the web editor.

Success criteria:

1. The whole loop (open page, tap word, see references, add or edit a face, save, approve) works on an
   iPhone with a short sequence of steps, in native iOS controls, in Arabic (RTL) and Dynamic Type.
2. The editor writes only through `/api/mushaf-1441/qiraat-review`; every write is the same RPC the web
   uses, so server rules (D8, narrator twice, wasl/waqf, version conflicts) and the edit log apply.
3. The reference matching (nquran, الشامل) and the draft rules give the same results as the web code,
   proven by golden tests that run the web's TypeScript over the real data.
4. **Nothing existing in the app changes**: reader, Qiraat layer, Mutshabehat, search, settings and sync
   look and behave as before. The editor is compiled only in DEBUG builds; a Release build contains none
   of it.

Non-goals: publishing to the App Store, an offline editor, editing the Quran text, any change to the web
app or its database schema.

## 2. Decisions and constraints

- **New decision (2026-10-05):** the developer editor may write to the web database, only through the
  web app's review API. `AGENTS.md` §1 ("never writes") is updated to say so. All other rules stand:
  everything lives under `apps/ios`, `ios/main` never merges into `main`, no keys or data committed.
- Entry point: one new row «محرر القراءات» in the existing `#if DEBUG` «المطور» section of the Settings
  sheet in `ReaderView.swift`. That is the only edit to an existing source file besides `project.yml`
  (new resources), `Makefile`, docs and tests.
- The editor has its own page view built on `MushafCore` (`PageLayout`, `QCFFontStore`). It does not touch
  `MushafPageView`, `PageController` or `MushafPager`.
- Online only. The Qiraat snapshot bundled with the app is untouched.
- Reference data (nquran 14 MB, الشامل 0.8 MB) is generated by a script from the web sources into
  gitignored `Generated/Review/` and bundled as resources. The repository is public: never commit it.

## 3. Architecture

### 3.1 MushafCore/Review (pure Swift, no UIKit, Swift Testing)

| Unit | Purpose |
|---|---|
| `ReviewModels` | Port of `types.ts`: `ReviewRow`, `ReviewPage`, narrators, flags, `HamzahDetail`, `CreateEntryInput`, `EntryFields`, suggestions, bulk types, errors. `Codable`, tolerant of missing keys. |
| `ReviewAPI` | `protocol ReviewTransport` (`Data` in/out) plus `URLSessionReviewTransport`; `ReviewAPI` exposes `page`, `overview`, `history`, `setStatus`, `update`, `setNarrators`, `create`, `delete`, `restore`, `undo`, `bulkDelete`, `findSameWord`, `copyEntry`, `findOccurrences`, `bulkApply`, `suggest`. Builds exactly the JSON the web route accepts and maps error codes (`VERSION_CONFLICT`, `RULE_D8`, `RULE_NARRATOR_TWICE`, `RULE_EMPTY_LOCATION`, `RULE_WASL_WAQF`, `UNDO_*`, `unavailable`, ...) to Arabic messages. 30 s timeout. |
| `ReviewDraft` | Port of `useReviewEditorDraft`: draft fields, narrators with action/wajh, multi-category selection, validation, wajh numbering (`nextWajhOrder`, Hafs floored at 2 with a note), save plan (primary entry plus sibling entries per extra category), dirty detection. |
| `ReferenceMatching` | Port of `nquranReference.ts` (`findNquranDifferencesForWord`, reader-label resolver, remainder computation), `shamilReference.ts` (entry match, `suggestShamilCategory`), `referenceGroup.ts` (`proposeReferenceDecision`, badge visibility), `referenceApply.ts`. Loaders read the bundled JSON per surah, lazily. |
| `NarratorDisplay`, `FacesSummary` | Reader-collapsing narrator names and colours, live faces summary. |
| `ReviewQueue` | Serial save queue (per entry/locus ordered, different ones parallel), optimistic rows with placeholder ids, undo on failure, retry, no duplicate creates. Pure; time and network injected. |

### 3.2 App layer (`Sources/ReviewEditor`, DEBUG only)

| View | Role |
|---|---|
| `ReviewEditorEntry` | Wrapped in `#if DEBUG`; full-screen cover from Settings. |
| `ReviewHomeView` | Page picker, whole-Mushaf progress from `overview`, jump to next unreviewed or flagged page. |
| `ReviewPageScreen` | Page canvas (`ReviewPageCanvas`, UIKit view on `PageLayout`): words tinted by status, selected-word ring, tap to select, swipe or buttons to turn pages, stats bar, save status bar, next/previous unreviewed word, next flagged. |
| `ReviewWordSheet` | Native bottom sheet (detents medium and large) with four steps: **الأوجه**, **المراجع**, **التحرير**, **اعتماد**. |
| `HamzahBuilderView`, `ImalahBuilderView` | Structured builders as pushed full-screen steps. |
| `ReviewHistoryView`, `SameWordView`, `ApplyAllView` | History with undo, copy from the same word, apply to all occurrences with preview. |
| `ReviewStore` (`@Observable`, `@MainActor`) | Holds page, rows, selection, draft, queue and status; the single object views bind to. |

Design language: system `NavigationStack`, `List`/`Form` grouped styles, SF Symbols, system colours and
materials, reader colours from the Qiraat catalog for readers and narrators, `.sensoryFeedback`
haptics, full RTL, Dynamic Type, VoiceOver labels, iPad uses the same sheet in a side-by-side layout.

### 3.3 Screens and the phone flow

Page screen: Mushaf page plus a compact top bar (page, surah, `‹ ›`) and bottom bar (progress, save
status, «التالي غير المراجع»). Tap a word, then the sheet:

1. **الأوجه:** the faces saved for this word (kind, category, narrators as reader-coloured chips,
   status chip). Per face: ✓ اعتماد, edit, ⚑ flag, 🗑 delete (with undo). Learned suggestions as cards with
   «➕ إضافة». «+ وجه جديد». A face covering several words is shown once.
2. **المراجع:** segmented nquran | الشامل (choice remembered). Groups for this word and ayah with the
   five reconciliation badges (matched, recorded unreviewed, partial, missing, unresolved). ➕ adds the
   group's narrators to the draft, with the description as «الأداء».
3. **التحرير:** فرش or أصول; category list (searchable, multi-select; Hamzah and Imalah categories open
   their builder); variant type and reading text for فرش; readers and narrators with presets and per-narrator
   action and wajh; وصل/وقف.
4. **اعتماد:** sticky primary button. With unsaved edits it reads «حفظ واعتماد», which saves and then
   approves the saved version in one queued step; otherwise «اعتماد». The sheet closes and the next
   unreviewed word opens.

Unsaved edits are flagged («تعديلات غير محفوظة»), and picking another word or leaving asks first.

### 3.4 Data flow

- `GET page` fills `ReviewPage` (words, rows, catalog, categories, variant types). Rows are matched to
  Mushaf words by `SSS:AAA:WWW` key. `overview` fills progress.
- Writes go through `ReviewQueue`; the page canvas and sheet update optimistically, the server row
  replaces the placeholder, a silent re-read runs once the queue is empty.
- After a successful save the existing `QiraatLiveSync.refresh(page:force:)` is called so the reader
  shows the change. This uses the app's current public API and does not alter the reader.
- Auth is the site's own session cookie, as `QiraatLiveSync` uses: the shared `URLSession` cookie jar.
  A random device id (UUID, `UserDefaults`) goes into every write for the edit log.
- Errors: `VERSION_CONFLICT` reloads the row and says so; rule errors are shown in Arabic next to the
  field; network failure keeps the draft and offers retry.

## 4. Safety

- Only the existing review API is called. No direct database access, no keys in the app.
- DEBUG only: `#if DEBUG` around the entry row and the whole `Sources/ReviewEditor` folder. A test builds
  Release and checks that no editor symbol is present.
- Automated tests use a stubbed transport. Anything against the real database is one page, with undo, and
  only with the owner's go-ahead at that moment.
- `make check-isolation` runs in `make test`.

## 5. Testing

- **MushafCore (Swift Testing):** model decoding against real captured responses, request building,
  error mapping, draft rules, queue behaviour, matching engines.
- **Golden parity:** `scripts/review_golden.mjs` (run with `tsx` from the web checkout) runs the web's
  `findNquranDifferencesForWord`, `proposeReferenceDecision`, `suggestShamilCategory`, `nextWajhOrder` and
  narrator display over the real reference data and real review pages, writes `Generated/Review/golden/*.json`
  (gitignored, regenerated), and Swift tests assert identical output.
- **App tests:** `ReviewStore` flows against a stub transport; XCUITest of the loop with a stub server
  injected by a launch argument; iPhone and iPad.
- Existing suites (100 core, 37 app) stay green; the reader UI tests prove nothing moved.

## 6. Milestones

M1 API client and models. M2 reference engines with golden tests. M3 page canvas, word sheet, review and
approve. M4 add and edit (فرش and أصول, readers, wasl/waqf). M5 Hamzah and Imalah builders. M6 history and
undo, suggestions, same-word copy, apply to all occurrences. M7 polish, iPad, accessibility, docs, final
review. Each milestone is committed on `ios/review-editor` only after its tests pass.
