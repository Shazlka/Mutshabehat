# IOS-12 — `MutshabehatCore` SPM package (Phase 1 scaffold)

Architecture is fixed below. Implement exactly this; do not add layers,
targets, dependencies or abstractions beyond it.

## Hard constraints

- **Xcode is NOT installed on this machine** — Command Line Tools only. The
  package must build and test with `swift build` / `swift test` against the
  host toolchain (Swift 6.4). Therefore: **no `import UIKit`, no
  `import SwiftUI`, no `#if os(iOS)`-only code paths, no `.xcodeproj`.**
  `swift test` passing is the definition of done.
- **Zero external dependencies.** `Package.swift` has an empty `dependencies:`.
  Use Foundation and the system `SQLite3` module only (`import SQLite3` links
  against the OS copy — verified working under CLT).
- Platforms: `.iOS(.v17)`, `.macOS(.v14)`. macOS is there purely so tests run
  without Xcode.

## `MutshabehatDomain`

### `ArabicText.swift`

A faithful Swift port of `src/lib/arabic.ts` (read that file first — it is the
reference implementation and carries the reasoning in comments).

Port these, as `public static` members of an uninhabited `public enum ArabicText`:

- `stripTashkeel(_:) -> String`
- `normalizeArabic(_:) -> String`
- `rasmSkeleton(_:) -> String`
- `normalizeArabicWithMap(_:) -> (norm: String, map: [Int])`
- `matchRanges(text:query:) -> [Range<String.Index>]`
- `ayahToInt(_:) -> Int` / `ayahToArabic(_:) -> String`

Porting notes — these are where a naive port breaks:

1. **Order matters.** Dagger alef `ٰ` (U+0670) becomes `ا` **before** tashkeel
   is stripped. `ٰ` is itself inside the tashkeel range, so stripping first
   deletes it and the normalisation is silently wrong.
2. The tashkeel class is the JS regex `[ً-ٰٟۖ-ۭ࣠-ࣾ‌-‏]` — i.e. the scalar
   ranges U+064B–U+0670, U+065F, U+06D6–U+06ED, U+08E0–U+08FE, and U+200C–U+200F.
   Match on **Unicode scalars**, not `Character`: Arabic combining marks form
   grapheme clusters with their base letter, so iterating `Character` will not
   see them separately. This is the single most likely bug in the port.
3. `map` in `normalizeArabicWithMap` indexes **UTF-16 offsets** in the JS
   original (`src[i]` over a JS string). Swift should use scalar or `String.Index`
   offsets consistently and return ranges as `Range<String.Index>`; just be
   internally consistent and make `matchRanges` return ranges valid for the
   input `String`. Do not expose raw Int offsets.
4. `normalizeArabic` trims; `normalizeArabicWithMap` deliberately does not.
   Keep that asymmetry — `matchRanges` depends on it.
5. `matchRanges` tier 2 bails when `rasmSkeleton(query).count < 3`, and pulls a
   leading `ا` into the highlight. Both are deliberate; keep them.

### `Entities.swift`

Plain `Sendable` value types mirroring the live production schema
(`docs/ios/DISCOVERY.md` §8.1). Domain types, not DB rows — use Swift types
(`UUID`, `Date`, `Bool`, enums), not `String`/`Int` stand-ins.

- `enum GroupStatus: String, Codable, Sendable { case draft, published, locked }`
- `enum PartType: String, Codable, Sendable` — `shared, diff, diff2, diff3, addition, unique, normal`
- `enum AnnotationType: String, Codable, Sendable` — `note, highlight, bookmark, favorite`
- `enum AnnotationTarget: String, Codable, Sendable` — `ayah, word, wordRange` (raw value `"word-range"`)
- `struct Group` — `id: UUID, userID: UUID, title, color: String, note/unote: String?, status: GroupStatus, favorite/completed: Bool, createdAt/updatedAt: Date, sourceAutomatedID: Int64?`
- `struct Verse` — `id: UUID, groupID: UUID, surah: String, ayah: Int, label: String?, sortOrder: Int`
- `struct Part` — `id: UUID, verseID: UUID, type: PartType, text: String, sortOrder: Int`
- `struct Annotation` — all 19 live columns; `tags: [String]`, `metadata: Data` (raw JSON).

The `ayah_key` format is `^[0-9]+:[0-9]+$` and `page_number` is 1...604 — model
these as a `struct AyahKey` and a validated `PageNumber` rather than bare types,
and give each a failable init. That is the only primitive-obsession fix worth
making here; do not wrap anything else.

### `Ports.swift`

Protocols the Domain owns and Persistence implements. Keep them narrow —
methods the app actually needs, not CRUD-by-reflex:

```swift
public protocol GroupRepository: Sendable {
    func allGroups() throws -> [Group]
    func group(id: UUID) throws -> Group?
    func verses(inGroup: UUID) throws -> [Verse]
    func parts(inVerse: UUID) throws -> [Part]
    func search(_ query: String) throws -> [Group]
    func upsert(_ group: Group, verses: [Verse], parts: [Part]) throws
    func delete(groupID: UUID) throws
}

public protocol AnnotationRepository: Sendable {
    func annotations(page: PageNumber) throws -> [Annotation]
    func annotations(ayah: AyahKey) throws -> [Annotation]
    func upsert(_ annotation: Annotation) throws
    func delete(id: UUID) throws
}
```

No `RemoteSyncGateway` — sync is Phase 3 (IOS-13). Do not scaffold it.

## `MutshabehatPersistence`

### `SQLiteDatabase.swift`

Minimal wrapper over the C API: open/close, `exec`, prepared statements with
typed binding/reading, and a `transaction { }` helper. Errors surface as a
`SQLiteError: Error` carrying the code and `sqlite3_errmsg`. **Never swallow a
non-OK return code.** Use `SQLITE_TRANSIENT` when binding strings/blobs — a
`nil` destructor with a Swift `String` is a use-after-free and it will not
reproduce reliably in tests.

Open with `sqlite3_open_v2`, enable `PRAGMA foreign_keys = ON` (SQLite defaults
it **off** — without this every `ON DELETE CASCADE` below is decorative) and
`PRAGMA journal_mode = WAL`.

### `Schema.swift`

`user_version`-based migration runner: an ordered array of migration closures,
applied in a transaction, each bumping `PRAGMA user_version`. Migration 1:

```sql
CREATE TABLE groups (
  id TEXT PRIMARY KEY NOT NULL, user_id TEXT NOT NULL,
  title TEXT NOT NULL, color TEXT NOT NULL,
  note TEXT, unote TEXT,
  status TEXT NOT NULL CHECK (status IN ('draft','published','locked')),
  favorite INTEGER NOT NULL DEFAULT 0 CHECK (favorite IN (0,1)),
  completed INTEGER NOT NULL DEFAULT 0 CHECK (completed IN (0,1)),
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  source_automated_id INTEGER,
  rasm_skeleton TEXT
);

CREATE TABLE verses (
  id TEXT PRIMARY KEY NOT NULL,
  group_id TEXT NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
  surah TEXT NOT NULL, ayah INTEGER NOT NULL,
  label TEXT, sort_order INTEGER NOT NULL
);
CREATE INDEX verses_group_idx ON verses(group_id, sort_order);

CREATE TABLE parts (
  id TEXT PRIMARY KEY NOT NULL,
  verse_id TEXT NOT NULL REFERENCES verses(id) ON DELETE CASCADE,
  type TEXT NOT NULL CHECK (type IN ('shared','diff','diff2','diff3','addition','unique','normal')),
  text TEXT NOT NULL, sort_order INTEGER NOT NULL,
  rasm_skeleton TEXT
);
CREATE INDEX parts_verse_idx ON parts(verse_id, sort_order);

CREATE TABLE mushaf_annotations (
  id TEXT PRIMARY KEY NOT NULL, user_id TEXT NOT NULL,
  annotation_type TEXT NOT NULL CHECK (annotation_type IN ('note','highlight','bookmark','favorite')),
  target_type TEXT NOT NULL CHECK (target_type IN ('ayah','word','word-range')),
  ayah_key TEXT NOT NULL, page_number INTEGER NOT NULL CHECK (page_number BETWEEN 1 AND 604),
  word_id TEXT, line_number INTEGER, word_index_in_line INTEGER,
  word_range_start_id TEXT, word_range_end_id TEXT,
  title TEXT, body TEXT, text_color TEXT, background_color TEXT,
  tags TEXT NOT NULL DEFAULT '[]', metadata TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  CHECK (target_type <> 'word' OR (word_id IS NOT NULL AND line_number IS NOT NULL AND word_index_in_line IS NOT NULL)),
  CHECK (target_type <> 'word-range' OR (word_range_start_id IS NOT NULL AND word_range_end_id IS NOT NULL))
);
CREATE INDEX annotations_page_idx ON mushaf_annotations(page_number, annotation_type);
CREATE INDEX annotations_ayah_idx ON mushaf_annotations(ayah_key, annotation_type);

CREATE VIRTUAL TABLE parts_fts USING fts5(
  norm_text, rasm_text, part_id UNINDEXED, tokenize = 'unicode61'
);
```

The CHECK constraints mirror production exactly (verified live — see
`DISCOVERY.md` §8.3). Keep them: they are the cheapest defence against a sync
bug writing garbage locally.

Notes:
- Postgres `tsvector` has no SQLite equivalent. FTS5 over **pre-normalised**
  text replaces it: on write, populate `parts_fts.norm_text` with
  `ArabicText.normalizeArabic(part.text)` and `rasm_text` with
  `ArabicText.rasmSkeleton(part.text)`. Search normalises the query the same
  way. That is what keeps iOS search agreeing with the web — do not tokenize
  raw Arabic and hope.
- Dates are ISO-8601 TEXT (UTC, fractional seconds) so rows round-trip against
  PostgREST unchanged in Phase 3. Use one shared `ISO8601DateFormatter` with
  `.withInternetDateTime, .withFractionalSeconds`.
- UUIDs are stored as lowercase `TEXT`; normalise on write. Swift's
  `UUID.uuidString` is UPPERCASE and Postgres emits lowercase — mixing them
  silently breaks every join and it is a nightmare to spot later.

### Repositories

Implement the two ports over `SQLiteDatabase`. `upsert(_:verses:parts:)` must
run in a single transaction and keep `parts_fts` in step with `parts`.
`search(_:)` queries FTS5 on `norm_text`, and falls back to `rasm_text` when
the normalised query returns nothing — the same two-tier behaviour as
`search_group_ids()` and `matchRanges` on the web.

## Tests

`swift test` must pass. Cover:
- every golden vector (above);
- migration runs from empty, is idempotent, and lands `user_version == 1`;
- `PRAGMA foreign_keys` is actually ON, and deleting a group cascades to its
  verses and parts;
- each CHECK rejects a bad value (bad `status`, bad `type`, `page_number` 999,
  `target_type='word'` with no `word_id`);
- round-trip a `Group` with verses and parts through upsert and read it back
  unchanged, including a `nil` note and a non-nil `sourceAutomatedID`;
- search finds a part by plene spelling when stored defective and vice versa
  (`السماوات` ←→ `السموات`) — this is the behaviour the whole normalisation
  layer exists for;
- UUID case-insensitivity: upsert with an uppercase UUID string and read back
  by lowercase.

Use in-memory databases (`:memory:`) in tests; no file I/O, no network.
