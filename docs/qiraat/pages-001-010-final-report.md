# Pages 1–10 Qiraat Ashr data — final report

## 0. Governing decision

The source PDF (`مصحف القراءات العشر-1.pdf`) was not present anywhere in this environment (checked:
no upload directory, no PDF on the filesystem, before any data work began). Per the task's own
rules, every record needs a visual PDF check before `verification_status = verified`, and guessing
is explicitly forbidden. Asked how to proceed, **the user chose: build the full architecture and
dataset now from the attribution/variant data typed directly into the task prompt, held at
REVIEWED tier, with the task's own flagged-uncertain items at NEEDS_MANUAL_REVIEW.** Everything
below implements exactly that decision — nothing in this batch is `VERIFIED`, and nothing is shown
to an ordinary (non-debug) user yet, by design.

## 1. What was built

- **Schema, reused, not duplicated** (`docs/qiraat/pages-001-010-existing-architecture.md`): the
  task's `qiraat_persons` is already `packages/qiraat-core/{readers,narrators,readings}.ts` from
  the earlier page-1 prototype (10 readers, 20 narrators, permanent IDs, already disambiguating
  `Q06-R01` "خلف عن حمزة" from reader `Q10` "خلف العاشر" — the task's own critical-identity rule).
  `qiraat_targets`/multi-word/multi-occurrence loci are a new optional `locusId`/`locusType` field
  on `QiraatVariant` grouping N independently-resolvable single-token records, not a new join
  table. A new `performanceNote` field carries phonetic-only differences
  (`variantText === hafsText`) so a pronunciation difference is never faked as a spelling change. A
  new `NEEDS_MANUAL_REVIEW` value was added to `VerificationStatus`, excluded from
  `PUBLIC_VERIFICATION_STATUSES` alongside `REVIEWED`/`MAPPED`/`EXTRACTED`.
- **Dataset** (`docs/qiraat/pages-001-010-word-mapping.md`, `data/qiraat/raw/pages-001-010.json`,
  `packages/qiraat-core/fixtures/pages/page-{001..010}.json`): 40 `QiraatVariant` records across
  10 pages / 28 conceptual loci, generated by the idempotent, reproducible
  `scripts/build-qiraat-pages-001-010.py`. Every `hafsText` is derived directly from the real,
  never-modified Mushaf-1441 word fixtures (not hand-typed) — see the reconciliation report §4 for
  the drift this caught and fixed. 36 records REVIEWED, 4 NEEDS_MANUAL_REVIEW (6 of the 40 records,
  spread across those 4 loci, carry empty `readingIds` because no attribution was confident enough
  to assert).
- **Wiring**: `packages/qiraat-core/repository.ts`'s `PAGE_VARIANT_LOADERS` now covers pages 1–10
  (was page 1 only); `/api/mushaf-1441/qiraat` needed no changes (already page-count-agnostic).
  Manually verified via a local production build (`next build` + `next start`) that every page 1–10
  returns its expected variant count in debug mode, that page 11 returns `[]` (the task's STOP
  boundary — page 11 and beyond were never touched), and that the public (non-debug) endpoint
  correctly returns 0 variants everywhere in this batch (nothing is VERIFIED/PUBLISHED yet).
- **UI**: the existing 3-mode Mushaf viewer, tap/detail panel, reader filter, and study-mode toggle
  from the page-1 prototype needed no new UI surface for pages 2–10 — they were already
  page-count-agnostic. What did need fixing for this batch specifically:
  - The قراءات detail-panel tab already distinguished NEEDS_MANUAL_REVIEW (red badge) from ordinary
    unpublished/REVIEWED (yellow badge) and performance-only display (no fake strikethrough diff),
    from earlier work in this phase.
  - **Found and fixed during this batch**: `comparisonMarkerForWord()` crashed
    (`computeAttribution requires at least one reading id`) when a NEEDS_MANUAL_REVIEW placeholder
    with empty `readingIds` was visible (debug "include reviewed" mode) — a real, reachable bug,
    since a reviewer opening exactly these records is the intended use of that mode. Fixed to
    return a neutral `unresolved: true` marker instead of guessing a color. The detail panel's
    "الباقون: N رواية بلا تغيير" line was also fixed to not appear for these records (it would have
    misleadingly implied the other 20 readings are confirmed unchanged, when the truth is simply
    "not yet determined"). See `pages-001-010-reconciliation.md` §5.
- **Tests**: 3 new regression tests added to `packages/qiraat-core/engine.test.mjs` (multi-word
  locus grouping, performance-only variant shape, the empty-readingIds crash guard); 2 existing
  page-1 tests updated to match the corrected مالك/ملك attribution and REVIEWED (not VERIFIED)
  status. 19/19 tests pass (`npm run test:qiraat`).

## 4. What this batch deliberately does NOT do

- **No record in this batch is `VERIFIED`.** The task requires a PDF page-image check before that
  status; no PDF was available. Consequently `data/qiraat/verified/pages-001-010.json` (the task's
  requested "verified" output file) is intentionally **not created** — there is nothing verified yet
  to put in it. Creating an empty or placeholder file for it would misstate what "verified" means in
  this project's own lifecycle.
- **Ordinary (non-debug) users see nothing new for pages 1–10 yet** — by design, since
  `PUBLIC_VERIFICATION_STATUSES` only includes VERIFIED/PUBLISHED. The feature is fully built,
  tested, and reachable via the existing debug "include reviewed" toggle for a human reviewer to
  cross-check against the actual PDF; promoting individual records to VERIFIED (or resolving the 5
  critical items) is a follow-up action once the PDF is available, not part of this delivery.
- **Page 11 onward was never touched**, per the task's explicit stop condition — confirmed both by
  `git status` (no fixture files beyond page-010.json) and by the live API returning `[]` for
  page 11.
- Playwright/Chromium screenshots were captured against a local production build for pages 1, 4, 6
  and 10 (comparison mode, plus the page-4 detail panel for the CRITICAL-REVIEW شاء الله
  placeholder) — see `pages-001-010-visual-verification.md`. Zero Qiraat-related console/page
  errors; the empty-`readingIds` crash guard (§1) was confirmed live, not just in the unit test.
